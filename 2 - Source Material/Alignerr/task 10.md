### Pros and cons

#### Model A:

- Pros:
Model A does a good job at separating concerns like assigning `includeCodeContext` as a toggle for the feature, while `numCodeContextLines` can be used to adjust number of lines from the context to be printed. This means we have more independent control over should the context be printed and how many lines should be printed. The `_format()` adds the snippet after the default `ic()` output when `includeCodeContext` is set to true, displaying rhe original value then the context lines. imports `linecache` to fetch the exact lines that are needed, as the imported `linecache` module caches the file ~~sata~~ data, it avoids re-reading the same file multiple times, which results in better performance. `linecache` is from std library which means no external dependencies, which means no (external) dependency issues. Tests like `test_code_context_disabled_by_default` are named well and do exactly what the name says. No limit to `numCodeContextLines`, offers freedom to the developer / debugger

- Cons:
The way context is displayed with the original line displayed first, followed by the context before the calling line then the lines after calling line. Can
be misleading and confusing.  The line format for context display is hard coded. No limit to `numCodeContextLines`, offers freedom to the developer but could flood the output when a beginner sets it to a large value like 100 or so without proper knowledge. Test names are descriptive and good but lack comments / docstrings. Proper handling of file permission issues is done, though the imported `linecache` silently does that.

#### Model B:

- Pros:
The snippets generated by Model B output is consistent with default  `ic()` logging, this is done by using the `startLine` and `icLine` and printing lines from the `srartLine` from where context needs to be printed for number of lines of context needed. Uses `getframeinfo()` from previously existing `inspect` module instead of importing an additional module. Has easy to understand code and simpler logic overall. When the code context is missing it simply returns early. `ic.contextLines` can be used to change number of context lines to print. Tests check for output alignment and align using spaces, the line numbering also verified after the `_snippet_lines(...)` extracts snippet lines from the output. Tests like `test_show_context_disabled_by_default` are descriptive and test for the name as described

- Cons:
Cannot be disabled simply using a parameter but `configureOutput(showC...=False)` must be called.  `contextLines` If modified on an instance, it only effects that particular instance but if its modified on a class, it affects all the instances and this could be problematic. No check if, `contextLines` is positive, `getframeinfo(....)` gets context information when `showCotext` is set `False`, this is not wrong but is inefficient. 

#### Justification for best overall
Comparatively speaking, Model B is a little bit faster than A as B does a single inspect call to read the context lines where as linecache in A does multiple calls to read the context. Also model B has a simpler and shorter code changes compared to A. Though A handles errors and has tests for more cases than B and does proper instance separation vs handling errors which is done by B. Also A is more flexible in usage of context display option where as in B its not even possible to disable simply using a parameter.

### Pros and cons

#### Model A:
- Pros:
model A keeps the implementation light weight using `inspect` instead of reading files directly and is aligned with the no new imports requirement and uses already existing `formatCodeContext()` etc.; for generating snippets. Reads the file once using `getframeinfo(...)` function, so it does not go through the file multiple times. `configureOutput(includeContext= ...)` can be directly used to toggle whether we need a snipper or not. Tests for feature being off by `default`, snippet can appear with or without any arguments etc.;
- Cons:
Model A prints snippet in wrong order. The required context lines are printed on top of the `ic |` line. This means the call site of `ic` and debug output are not properly formatted inline. `numCodeContextLines` having negative values is not checked for, this is because both if these are not tested which are direct requirements. So A needs to insert `ic |` in proper position immediately after the `>>>` marker line. Limit the the values of `numCodeContextLines` to 0. Add enough tests like the above two and testing for missing source code. 

#### Model B:
- Pros:
Mobel B also avoids any additional imports. The `ic |` output is inserted right after the `>>>` marker line. negative line counts are checked for in `numCodeContextLines` and is clamped to values above 0 using `max(.., 0)` . Adds separate tests specifically like line numbers in basic snippets to whether negative values are clamped to be 0 or more. 
- Cons:
The snippet doesn't always properly align with `ic.prefix` widths, fixed 4-space indent. No tests for missing source code. Reads the entire file into memory which could be a problem for heavy files. If the file being read from changes between runs snippet doesn't show the changes. Also doesn't test for missing source code. `contextLines` being global is a big downside as global`contextLines` attribute when changed would change all the instances.

#### Justification for best overall
Both models implement the snipper feature but are different in the style of snippet, way of generating, testing depth. Model A is bit more configurable to be configed for a single instance, where as Model B is much more simple and also has better testing and error handling. Model A used `linecache.getline()` while Model B used `getframeinfo(..., context=...)`. Both of them do the required job but miss checking for the behavior when there is missing source as there no tests for this in both the models. Model B aligns snippets with a set / given width. MOdel A uses `lineCache` and its more resistant to misbehave during file changes mid run, where as Model B uses `code_context` and if this is missing the whole snippet can be empty. The global`contextLines` attribute when changed would change all the instances and is a huge downside.
